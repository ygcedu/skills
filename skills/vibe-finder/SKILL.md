# Vibe Finder — 自主改进发现器

## 目标

扫描项目代码库，主动发现可以改进的地方，生成一份结构化的任务清单，帮助用户（或另一个agent）知道"接下来该做什么"。

## 工作流程

### 1. 扫描阶段 — 多维度探索

按以下七个方向逐一扫描项目，每个方向列出 **2-5 个**最值得做的改进点：

| 方向 | 扫描重点 |
|------|----------|
| **代码质量** | lint错误、类型不一致、死代码、重复逻辑、命名不规范、缺少注释 |
| **库替代** | 自封装方法可被成熟第三方库替代、重复造轮子、未用现成解决方案 |
| **测试** | 覆盖率缺口、边界条件缺失、测试重复setup、未测试的错误路径 |
| **架构与结构** | 过大文件（>500行）、循环依赖、硬编码值散落各处、目录结构混乱 |
| **性能** | N+1查询、循环内IO、重复计算、不必要深拷贝、可懒加载模块 |
| **安全** | 硬编码密钥/token、未校验的用户输入、已知CVE依赖 |
| **用户体验**（前端） | 缺失错误提示、无loading状态、无障碍缺陷、响应式断裂 |
| **文档** | README过时、缺少JSDoc/Docstring、未记录的变更 |

扫描方法：
- 用 `find` / `glob` 定位大文件、配置文件
- 用 `grep` / `Grep` 搜索常见bad pattern（`console.log(`、`any`、`TODO`、`FIXME`、硬编码密码模式等）
- 读关键入口文件理解项目结构
- 检查 package.json / requirements.txt 等依赖列表

### 2. 评估阶段 — 为每个发现打分

对每个发现的改进点，评估以下维度：

**复杂度**（执行难度）：
- `S` — 一行改动或简单替换
- `M` — 需要改2-3个文件，涉及少量逻辑调整；
         或纯机械式重构（组件封装、重复代码抽离、
         大文件拆分、命名规范化），不涉及业务逻辑变化
- `L` — 需要改多个文件，涉及重构或新抽象

**工作量**（预估时间）：
- `~15min` — 快速修复
- `~1h` — 中等改动
- `~半天` — 较大改动
- `~1天+` — 需要深入思考的设计级改动

**影响面**（受益范围）：
- `低` — 只影响单个文件或模块
- `中` — 影响多个模块或提升整体代码可读性
- `高` — 影响整个项目（性能、安全、核心架构）

**优先级** — 用四象限法排列：

```
          高影响
            │
    B 紧急重要 │  A 明星项目
  (高影响+中低复杂度)  (高影响+高复杂度)
            │
────────────┼────────────
            │
    D 填充物 │  C 优先执行
  (低影响+低复杂度)  (低影响+高复杂度)
            │
          低影响
```

- **A区（明星项目）** — 高影响 + 高复杂度：值得做但需要排期
- **B区（紧急重要）** — 高影响 + 低复杂度：立即做，性价比最高
- **C区（优先执行）** — 低影响 + 高复杂度：先别做，除非有明确需求
- **D区（填充物）** — 低影响 + 低复杂度：有空就做，不紧急

### 3. 输出格式

生成如下结构的清单：

```markdown
## 改进建议清单

### A区 — 明星项目（高影响 × 高复杂度）

| # | 方向 | 改进点 | 涉及文件 | 复杂度 | 工作量 | 预期收益 | 执行顺序 |
|---|------|--------|----------|--------|--------|----------|----------|
| 1 | 测试 | ... | ... | L | ~1天+ | ... | 第1步 |

### B区 — 紧急重要（高影响 × 低复杂度）⭐ 推荐优先

| # | 方向 | 改进点 | 涉及文件 | 复杂度 | 工作量 | 预期收益 |
|---|------|--------|----------|--------|--------|----------|
| 1 | 安全 | ... | ... | S | ~15min | ... |

### C区 — 优先执行（低影响 × 高复杂度）

| # | 方向 | 改进点 | 涉及文件 | 复杂度 | 工作量 | 预期收益 |
|---|------|--------|----------|--------|--------|----------|

### D区 — 填充物（低影响 × 低复杂度）

| # | 方向 | 改进点 | 涉及文件 | 复杂度 | 工作量 | 预期收益 |
|---|------|--------|----------|--------|--------|----------|
```

在清单末尾附上 **执行建议**：
- 推荐从 B 区开始，快速获得回报
- 说明各区间任务的依赖关系（比如"先修好类型再补测试"）
- 标注哪些可以并行执行

### 4. 执行阶段 — 用 Paseo 工具派发子agent并行处理

当用户确认要执行任务时，按以下步骤派发：

#### 4.1 按文件分组，确保无冲突

将任务按修改的文件分组。**同一文件的任务必须放在同一个agent里**。不同文件的任务可以并行。

#### 4.2 为每组任务创建 Paseo worktree

使用 `create_worktree` 工具：

```
create_worktree(target: { kind: "branch-off", branchName: "fix/简短描述" })
```

- 每个worktree对应一个agent的工作组
- `branchName` 要简洁描述任务内容（如 `fix/types`、`perf/hit-detection`）
- 返回结果中包含 worktree 路径和分支名，记录下来供后续使用

#### 4.3 创建子agent并分配任务

使用 `create_agent` 工具，参数说明：

```
create_agent(
  relationship: { kind: "subagent" },     // 子agent，报告给你
  workspace: { kind: "current" },          // 在当前workspace运行
  title: "fix/types — 类型安全修复",       // 简短描述，<=60字符
  provider: "<当前agent的provider>",       // 使用和父agent相同的provider，除非用户特别说明
  initialPrompt: "你在worktree {worktree_path} 中，分支 {branch_name}。\n\n请修复以下任务：\n- 任务1: 具体描述 + 文件路径 + 行号\n- 任务2: ...\n\n完成后提交commit，message格式: [fix]/[perf]/[chore]:[模块] 描述\n\n注意：不要改动其他文件。"
)
```

- **provider 必填** — `create_agent` 要求显式传入 provider，默认使用和父agent相同的provider，除非用户特别说明用不同的模型
- 每个agent处理一组**无文件冲突**的任务
- 最多并行4-5个agent，避免上下文过载
- 在 `initialPrompt` 中必须明确告知：
  - worktree路径和分支名
  - 具体改什么（文件路径 + 行号 + 改动内容）
  - 提交commit的message格式
  - 不要改动其他文件

#### 4.4 等待agent完成，收集commit hash

每个agent完成后会收到通知。记录其commit hash，用于后续合并。

#### 4.5 Cherry-pick合并到main

```
git cherry-pick <commit_hash>
```

每个agent的commit cherry-pick到main主分支。如果某个agent没有产生有效commit（如文件未改动），跳过。

#### 4.6 清理worktree

使用 `archive_worktree` 工具：

```
archive_worktree(worktreePath: "/path/to/worktree")
```

所有commit合并成功后，清理所有worktree。

## 注意事项

- 不要为了填满清单而找改进点，宁缺毋滥
- 每个发现点必须附带具体文件路径和行号范围
- 如果某个方向确实没有发现任何问题，标注"未发现明显问题"即可，不要编造
- 优先关注当前正在活跃开发的模块
- 尊重现有代码风格，改进建议应是渐进式的，不是推倒重来
